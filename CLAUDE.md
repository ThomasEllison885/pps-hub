- **Pipeline: the caret fell out of the cell you tabbed into (2026-08-31, `3086552`).** Rachel: *"This feels nitpicky but when I'm working in the pipeline and I try to tab over to the next section, I still have to click in the box to start typing."* Not nitpicky and not tab order — a race with the save. Tabbing out of a cell fires `onblur` → `saveField` → POST; focus moves to the next cell correctly; then a few hundred ms later the response arrives and `patchEntryInPlace` does `old.replaceWith(fresh)`, **replacing the row including the element she is sitting in**, and focus falls back to `<body>`. Type slowly or on a fast connection and you never see it, which is why it reached us as an apology instead of a bug report. **Measured in Chromium at 250ms latency: focus after the save lands `<body>` → next cell; textarea caret 0 → preserved; tabbing off a number field `<body>` → next cell.** No data was ever lost — the typed value survived either way, because the replacement itself triggers a blur that saves it. Only the cursor.
  - **The hazard was already known here, on the other caller.** The 3s poll has guarded it for a while ("Never stomp a row while the local user has a field in it focused"). The save path never got the same protection. **But the poll's answer — skip the patch — is wrong on this path**, because the save response is how server-derived values arrive: blurring `property_name` fills `client_contact` from the Hub and that reaches the page *only* through this patch. Skipping it would trade a lost caret for a lost auto-fill. So the caret is carried across the replacement instead of the replacement being avoided, and the poll's guard stays exactly as it is. Two callers, two different right answers.
  - **`defaultValue` decides whose value wins, with no bookkeeping.** It holds what `renderRow` wrote into the markup, so `value !== defaultValue` means "typed here since this row was drawn": her keystrokes win if she has, the server's value wins if she has not — which is what lets an auto-filled `client_contact` still appear in a field she merely tabbed into. Excluded for `<select>`, where `defaultValue` means nothing and status would look permanently dirty.
  - **Three quirks the restore has to survive**, each with its own test: Chrome throws `InvalidStateError` reading `selectionStart` on `<input type="number">` — which is exactly Amount and Sub Pay — so both the read and the write are in try/catch; `focus({preventScroll: true})`, because focusing scrolls into view by default and a save landing while the board is scrolled sideways would yank the viewport back, undoing `beebb0e`; and a re-`autoGrow` after restoring a textarea value, or Project/Notes come back one line high with text hidden inside. **One accepted side effect:** restoring focus re-fires `onfocus`, so a patch landing while she is in `client_contact` reopens the suggestion dropdown and sends one extra presence ping. Both are correct-if-surprising — she really is focused there.
  - **Worth generalising: "this feels nitpicky" is a tell.** The reports that are hard to describe are often the ones with a race behind them, because the symptom moves around. Nothing about the phrasing here matched the actual defect, and the word "tab" pointed at tab order, which was never wrong.

- **Connection pooling (2026-08-25) — F-05 closed. `db_pool.py` is new; read this before touching `get_db()`.** `get_db()` opened a fresh connection on every call, and the dashboard calls it — directly and through ~15 helpers — **21 times per page load**. Measured over a local UNIX socket: 61ms to render, **44ms of it (72%) pure connection setup**, at 2.1ms a handshake; on Render the database is over the network with TLS where a handshake costs several times that. Peak concurrency was 9 open at once and 7 were never explicitly closed. After: **0 new handshakes once warm, 12–14ms render.** Verified end to end through the real Flask route against a scratch Postgres, and `/admin/system-state` now has a **DB pool** row so the same thing can be checked on Render (reused climbing while created stays flat is the healthy shape).
  - **It does not use `psycopg2.pool`, and the reason is genuinely surprising.** `AbstractConnectionPool._putconn` keeps a returned connection only while `len(self._pool) < self.minconn`; otherwise it calls `conn.close()`. So `ThreadedConnectionPool(1, 10)` — the obvious spelling — keeps **one** idle connection and closes every other one handed back. On a page that checks out nine at once, eight are destroyed on return and reopened next load, i.e. it would not have fixed anything. `minconn` there is not "the floor", it is "how many we bother keeping". `tests/test_db_pool.py::test_psycopg2_pool_discards_returned_connections` pins that against the installed psycopg2 so the claim is checkable and so we find out if it ever changes. **Do not "simplify" this module by swapping in psycopg2's pool.**
  - **Four invariants, each with a test that fails without it.** (1) *A connection handed out is always in a clean transaction state* — rolled back on release and validated on acquire; no caller has ever had to cope with inheriting an aborted transaction and none will start now. (2) *Exhaustion is never an error* — `acquire()` returns None and `get_db()` opens a direct connection, exactly the old behaviour; a queue here would stall requests behind gunicorn's 120s timeout. (3) *A dead connection is never handed out* — every acquire does a `SELECT 1`, because Render restarts Postgres and `.closed` does not notice; a round trip is a fraction of a handshake and the alternative is one stale connection recycled forever. (4) *Nothing is shared across a fork* — gunicorn runs without `--preload` so each worker builds its own; the pid guard **abandons** inherited connections rather than closing them, since closing an inherited socket sends a Terminate for a backend the parent is still using.
  - **`DB_POOL_DISABLED=true` is the kill switch, `DB_POOL_MAX` the size (default 10).** Same reasoning as `SERVICE_WORKER_DISABLED`: this sits under every query in the Hub, so backing it out has to be an env var and a restart, not a deploy. Verified: with it set, the dashboard goes straight back to 21 handshakes and 64–78ms. Two workers means at most 2 x `DB_POOL_MAX` sockets against Postgres — raise it knowing that.
  - **The `teardown_request` hook is load-bearing, not tidiness.** Seven of the 21 connections a dashboard load took were never closed by their caller; rather than audit 107 call sites, the request that took them gives them back. With the hook disabled the pool drains to its cap within a few loads (`in_use` pinned at 10, `idle` 0, 227 overflows across twelve loads) and **the app keeps working**, silently falling back to direct connections — which is exactly why nobody would notice. Background threads (the proposal-diff emailer) have no request context, are deliberately not tracked, and must close their own.
  - `init_db` and the `auth_tokens` migration now use try/**finally**. They run outside a request so the teardown hook cannot cover them, and a raise anywhere in init_db's several hundred statements used to skip the close — measured as `in_use` stuck at 1 from process start, one of ten slots gone for the life of the worker.
- **`init_db` silently discarded almost the entire schema on a fresh database — fixed 2026-08-25, `db_ddl.py`.** This is the entry from the day before, which understated it twice: it was not four sites, and the consequence was not a half-built schema. **Measured on an identical virgin Postgres: before, `init_db` left 1 table. After, 49.**
  - **Why it was that bad.** In Postgres a failed statement aborts the whole transaction, so `except: pass` does not recover — it silences the cascade. `init_db` creates ~40 tables and commits once at the end, and **a commit on an aborted transaction is a rollback**. So one skipped statement early on threw away every table created after it, reported as a single "DB init error" line. `tests/test_db_layer_db.py::test_commit_on_an_aborted_transaction_silently_rolls_back` is that mechanism on its own.
  - **The count.** Fifteen swallowed-DDL sites in `init_db` (not four), one in `pipeline_board.init_tables`, and one `try` in `ask_pps.init_tables` wrapping nineteen statements. The statement that actually killed a virgin run was **not** DDL at all: a backfill `UPDATE knowledge_entries ... FROM knowledge_prompt_answers` that runs before that table exists.
  - **The fix is a savepoint per statement, never `conn.rollback()`** — a rollback in the except would clear the aborted state and also discard every table `init_db` had already created, which is worse than the bug. `db_ddl.checkpointed(cur)` wraps a cursor so **schema statements only** (ALTER / CREATE / DROP / COMMENT) get a savepoint; adopting it is one line at the top of an `init_tables`. Ordinary DML still raises exactly as before — swallowing an INSERT that seeds a user row, or a SELECT whose rows the next line fetches, would turn this from a fix into a better-hidden version of the same bug. The handful of genuinely best-effort backfills are marked one by one with `db_ddl.optional_step` (two in `ask_pps`, two in `init_db`), which says "this may not apply" at the call site instead of hiding it in an `except`.
  - Every skip now prints its statement and error, so a schema statement that starts failing is louder than the one opaque line it used to produce. A virgin run logs 5 expected skips and creates 49 tables; a second run on the same database logs 0 and is a clean no-op.

## Design decisions that look like bugs but aren't

- **The daily digest and the weekly recap count differently, on purpose (Thomas, 2026-08-31).** Both were raised as accuracy findings during the 2026-08-31 digest audit and both came back as decisions. His words: *"Logins are positive and any action are good. The actual number isn't as important as they are actually doing it. Not for my daily email.   **The daily digest answers "is the team using the Hub". The weekly recap answers "who did how much".** Two questions, two counting rules. The line between them is not rigour — it is that **the weekly is a ranked comparison between people and the daily is not**, so anything a person could inflate has to be bounded in the weekly and needs no bounding in the daily.

  - **Hub logins count toward the daily total** and appear in AT A GLANCE. Reads like counting attendance as work. ## Hard-won lesson: nothing slow at import scope, or the app never binds a port

2026-08-21: the password campaign was called from the bottom of `app.py`, so it ran **during module import** — up to thirteen synchronous SMTP sends, each with a 30s timeout. Gunicorn cannot bind a port until the module finishes importing, so Render's port scan timed out first and cancelled the deploy with `==> No open ports detected` / `Port scan timeout reached`. The reset emails had already gone out against the shared database by then, so the failed deploy still changed production state — and because the run had claimed itself in Postgres *before* doing the work, a retry would have skipped everyone and left the job permanently half-done.

**Takeaway for either agent:** module scope is for definitions. Anything that talks to SMTP, loops over the roster, or waits on a network belongs behind a route, a cron, or a background thread — never at import. If you find yourself writing "runs once on deploy", that means a cron or an owner-triggered endpoint, not a call at the bottom of the file. And when a one-shot job mutates production, make it **resumable and idempotent from observable state** rather than gated on a flag you set before starting: the first attempt will be interrupted eventually, and "did this already run?" has to be answerable from the data itself. `password_campaign.pending_user_keys` is the worked example.

Related, same class: `--timeout 120` kills a worker mid-request, so long synchronous work in a *route* is the same mistake one layer up — see the COI vision-pass chain above and `time_budget_seconds` in both `insurance_compliance` and `password_campaign`.

## Hard-won lesson: don't put the whole Hub on a single worker

2026-07-29: shipped Pipeline Board with Socket.IO, which needed a single gevent gunicorn worker (`render.yaml`/`Procfile`) to get real-time push. Result: Hub-wide lag, reported within hours — one worker means *any* blocking call anywhere in the app that doesn't cooperate cleanly with gevent's monkey-patching (Claude API calls, docx/xlsx generation, none of which were audited for this) stalls the entire process, so one slow request anywhere freezes every other request, dashboard included. Reverted same day to `--workers 2` sync, no monkey-patching, and reworked Pipeline Board to plain HTTP polling instead of Socket.IO.

**Takeaway for either agent**: this app's worker/concurrency model is shared infrastructure for every feature, not just whichever one you're building. Don't change `render.yaml`'s `startCommand`/worker class for a single feature's benefit without auditing every blocking I/O path in the app (Claude API, email, file generation) against whatever concurrency model you're proposing. For anything at this app's current scale (a handful of pilot users), a 3-5s client poll against normal REST endpoints gets 95% of the "feels live" UX with none of the shared-infrastructure risk — prefer it over WebSockets/Socket.IO unless there's a demonstrated, specific need polling can't meet.

## Conventions worth both tools following

- **Daily digest usage:** new Hub modules must show up in the nightly email. Features with their own log table (`proposal_log`, `ppm_log`, …) are already queried in `daily_digest.collect_digest_items`. Everything else calls `hub_usage.record_usage(get_db_fn, user_key, feature, action, title, meta)` on discrete actions (opens, runs, imports, generates) — **not** on polls/heartbeats. The digest reads `hub_usage_events` automatically; do not add a new SELECT per feature. Pipeline Board cell edits are summarized from `pipeline_board_entries` (too chatty to log per keystroke).
- **Scheduled jobs must record their runs.** Any new cron endpoint calls `system_state.record_job_run(get_db, '<slug>', result)` after it finishes, and gets a line in `system_state.KNOWN_JOBS` so it appears on `/admin/system-state` even before its first run. Same reasoning as the `record_usage` convention above: a job nobody can see the status of is a job that can stop firing silently. Do not invent a second place to store this — it goes in `hub_settings` under `job_last_run:<slug>`.
- Shared SOP language that appears in both curricula (e.g. callback communication tone in `ops_callbacks` / PM Week 4) should stay **word-for-word identical** between `psc_training_data.py` and `pm_training_data.py` — check both files when editing either.
- New DB tables for trainee-facing features mirror the existing `psc_training_*` / `pm_training_*` naming and shape (progress / notes / feedback / enrollment / manager_signoffs).
- Thomas's writing-voice reference lives at `docs/thomas_voice.md` — check it before drafting anything in his voice (proposals, emails, Hub copy).
